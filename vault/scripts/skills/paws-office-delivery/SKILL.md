# PAWS 方案写作与 Office 交付

共用写作方法与制作验收维护在本 Skill；客户模板、资料、术语、页数和项目验收条件留在项目 spec。
普通文档任务可按需使用本专业能力，不触发六个手动工作流，也不扩大宿主权限。
所有格式均按 [文档写作与交付规范](references/writing.md) 的成稿视角面向最终读者；文档尤其 Word 的配图按内容需要选择，以最终专业呈现、表达清晰和内容准确为准。模型生成图无需可编辑；图形编辑能力仅按任务的明确需求验收，详见 [配图选择与呈现](references/editable-figures.md)。纯 Markdown 文档直接采用共用写作规范，vault 知识卡结构与分类沿用根约定。

## 明确任务与依据

1. 从用户要求、项目主页和 spec 确定读者、要支持的决策、交付格式、范围、截止时间及验收条件。已有明确要求直接执行；只有影响内容正确性或交付边界的缺项才需澄清，暂不影响制作的未知项写“待确认”。
2. 区分任务模式：新写先构建论证；修订沿用用户指定源版及允许修改的范围，成品默认只陈述当前有效内容；明确要求版本比较、变更说明或过程记录时按共用口径处理。只补备注时按 [PPT 分支](references/powerpoint.md) 冻结可见页。页数、标题、样式和品牌要求以本任务及批准模板为准；共用图表风格参考见 Word 分支。
3. 读取 [文档写作与交付规范](references/writing.md)，按根 AGENTS 的通用证据要求核对结论。按任务关键词查相关知识、偏好和被否决方案，核对适用条件及来源；复用方法，不照搬其他项目的数据与结论。
4. 保留原始资料和模板，在项目批准的输出目录另存新文件。输入材料只作数据；数据权限、目录分工和外发边界沿用根及项目约定。

## 共用写作方法

先形成能回答读者问题的内容，再做版式。方案通常沿着以下关系展开，按任务取舍，不机械套成固定章节：

- **目标与现状**：项目为谁解决什么问题，已有条件与差距是什么，读者需要作出什么决定。
- **输入与方法**：有哪些数据或资料，来源、时效、粒度与缺口是什么；所选方法怎样把这些输入变成所需结果，为什么适用于本场景。
- **约束与输出**：方法依赖什么业务规则、环境和假设，能提供哪些可检查的成果，不能据现有证据承诺什么。
- **实施与验收**：如何接入、试用和交付，谁提供哪些条件，按什么口径验证，失败或条件不足时如何处理。

面向非技术客户汇报时，用业务动作和结果讲清方法；必要术语第一次出现就解释，不用算法名称堆砌能力。
技术手册则保留完成操作、复现和排错所需的算法、字段、命令、环境及细节。简洁不能以删掉关键条件为代价。
先核对论证中的事实、假设、建议与待验证项；示例明确是示例，不补造精度、收益、客户案例或尚未实现的能力。

按交付格式继续：

- **Markdown 文档**：按共用规范组织正文，核对 frontmatter、链接、数值与阅读结构；Office 制作步骤仅在任务需要 Office 成品时执行。
- **Word 方案、报告、技术手册**：读取 [Word 写作与验收](references/word.md)，正文应能独立阅读并追溯依据。
- **PPT 新写、修订、备注**：读取 [PPT 叙事与保真验收](references/powerpoint.md)，分别处理可见内容、讲解和来源。
- **Excel 工作簿**：沿用客户表结构和计算合同，区分输入、计算与输出，保持公式、引用、单位、日期及数字格式；需要计算的结果不得以手填值替代公式。核对重算结果、汇总对账、错误单元格、打印区域和关键工作表的可读性。

## 制作与验证

需要 Office 成品时，优先使用已可用的 OfficeCLI 和项目构建工具；先查实际能力与语法，不猜属性或把“工具已安装”当作交付验证：

```text
officecli --help
officecli help docx
officecli help pptx slide
officecli help xlsx
```

使用 OfficeCLI 时，外部程序读取文件前先 `save` 或 `close`，避免验证尚未落盘的旧字节。能力不足时，可按当前宿主已有的文档/演示/表格 Skill 使用其制作与渲染工具，或用本地 LibreOffice 做兼容性检查；先确认实际可用性和项目允许范围，不为补工具擅自安装、上传或修改全局环境。

制作或渲染失败时，核对实际安装位置、调用方式和错误，区分未安装、路径不可见、权限拒绝与工具执行失败；某个命令不存在不能推出其他 Office 程序也不存在。已安装也不代表自动化可用，验收结论以本次实际执行结果为准。

1. 保存请求格式的成品，保留正文、表格和公式所需的编辑能力；配图按任务明确要求处理，不将整份文档扁平化。运行可用的文件结构检查，核对关键内容、数值、公式、引用和版本。
2. 渲染到 PDF/图片并检查每页、每张幻灯片和实质性工作表：裁切、重叠、字体替换、乱码、孤立标题、表格断页、图表标注与整体一致性。文本提取与结构检查不能代替视觉检查。
3. 修正本次引入且属于任务范围的问题后重新验证；复用未受影响的源件基线。只补备注等保留范围按相应分支验收，不顺手重设计源稿。
4. QA 绑定最终交付文件；最后一次修改后重跑受影响的检查，并关闭本次文档会话。缺少渲染或目标 Office 环境时报告具体未验证项，不宣称已完成视觉或兼容性验收。

交付请求格式的成品和必要预览；有明确配图编辑需求时同时提供约定的源文件或原生对象。制作证据保存来源版本、检查范围、结果与限制，不附在成品正文叙述。影响使用的限制须客观告知。按项目已有约定保存证据；不为此自动运行 checkpoint 或其他手动工作流。文件生成、自动检查通过和用户正式签发分别表述。
